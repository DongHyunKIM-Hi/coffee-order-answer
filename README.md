# 2단계 — 예외 처리와 시나리오

> [!NOTE]
> 과제의 **모범 답안**입니다. 정답은 하나가 아니며, 좋은 구현의 한 예시입니다.
> 단계는 커밋으로 나뉘어 있습니다: `step1`(정상 경로) → `step2`(예외 처리) → `step3`(최종). `git checkout`으로 오갑니다.
>
> 이 단계에서 `bash check-scenarios.sh`를 돌리면 **10/12**가 나옵니다. 같은 사용자의 동시 주문·동시 충전 두 가지만 실패하는 것이 설계대로입니다. `@Transactional`만으로는 막히지 않고, 3단계의 분산 락이 필요합니다.
해설 영상용 단계별 코드의 두 번째 단계입니다. 단계 구분과 실측 결과는 `docs/stages.md`에 있습니다.

- **추가하는 것**: 입력 검증과 에러 응답(400 / 404 / 409), 주문과 포인트 차감을 한 트랜잭션으로 묶기,
  데이터 수집 플랫폼 전송, 인기 메뉴의 최근 7일 범위.
- **여전히 하지 않는 것**: 동시 요청 보호(분산 락·조건부 UPDATE·비관적 락), 전송 실패 대책(아웃박스와 재전송),
  Redis 집계와 장애 폴백. 이 셋이 3단계의 주제입니다.

```bash
docker compose up -d --wait   # MySQL 8.4 (3306), Redis 7.4 (6379)
./gradlew bootRun             # 8080
```

- 2단계도 Redis를 쓰지 않습니다.
- 3잔 값만 충전하고 동시에 10건을 주문하면 **10건이 모두 성공합니다.** `@Transactional`을 붙였는데도 깨지는
  이유는 `OrderService`, `PointService`, `UserPoint` 주석에 적어 두었습니다.
- 테스트 코드는 없습니다. 테스트는 3단계에서 다룹니다.
